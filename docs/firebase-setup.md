# Firebase setup

Court Fix uses Firebase Authentication and Cloud Firestore on the Spark plan. The website deliberately has no public account creation form: create the two user accounts in Firebase Authentication, then share their sign-in credentials privately.

## Create the Firebase project

1. Create a Firebase project and select the no-cost Spark plan.
2. Add a Web app in Project settings and copy its web configuration.
3. Enable **Authentication → Sign-in method → Email/Password**.
4. Create the two user accounts under **Authentication → Users**. Users can set their own password from the app's **Forgot your password?** link.
5. Create a Cloud Firestore database. Choose a location close to the users.
6. Publish the repository's `firestore.rules` in **Firestore Database → Rules**.
7. Generate a VAPID key pair for direct Web Push using the Java helper below. Do not use the Firebase Cloud Messaging key pair: this app uses the browser Push API directly, and the Java sender needs the matching private key.
8. Copy `site/firebase-config.example.js` to `site/firebase-config.js`. Fill in the web configuration and generated public VAPID key. `site/firebase-config.js` is ignored by Git.

Before deploying, add the GitHub Pages hostname (for example, `your-account.github.io`) to **Authentication → Settings → Authorized domains**.

## Deploy with GitHub Pages

The `Deploy Court Fix web app` workflow publishes the `site/` directory to GitHub Pages whenever site files change on `main`. It generates the ignored `firebase-config.js` during the workflow from two public repository variables:

- `FIREBASE_CONFIG_JSON`: the complete Firebase web config object as JSON, for example `{"apiKey":"...","authDomain":"court-fix.firebaseapp.com","projectId":"court-fix","appId":"1:...:web:..."}`. Include any other fields from the Firebase console if present.
- `VAPID_PUBLIC_KEY`: the public value generated by `tools/VapidKeyGenerator.java`.

Set these under **GitHub repository → Settings → Secrets and variables → Actions → Variables**. These are public client-side identifiers; no private key belongs there. Then select **GitHub Actions** as the Pages build and deployment source under **Settings → Pages**. The first deployment runs after the workflow is committed and pushed to `main` (or can be started from the Actions tab).

After deployment, open the Pages URL on the iPhone, add it to the Home Screen, launch it from the Home Screen icon, sign in, and tap **Enable notifications**. iOS web push requires an installed Home Screen web app and user permission.

The web configuration and public VAPID key are designed to be included in client code. Never put a Firebase service-account private key or VAPID private key in the site. The generated private key is saved locally as `vapid-private.key` (ignored by Git); its single-line contents belong only in the GitHub Actions `VAPID_PRIVATE_KEY` secret.

## Generate the Web Push key pair

From the repository root, compile and run the Java 25 helper:

```sh
mkdir -p target/tools
javac -d target/tools tools/VapidKeyGenerator.java
java -cp target/tools VapidKeyGenerator
```

The helper prints the public key for `site/firebase-config.js` and saves the private key to `vapid-private.key` with owner-only permissions. Keep that file private. Replace `YOUR_PUBLIC_VAPID_KEY` in the local Firebase config with the printed public key. The private key is not needed by the app yet; it will be added as a GitHub Actions secret when push delivery is implemented.

## Data layout

- `users/{uid}/preferences/main` stores that user's selected court IDs and weekly time windows.
- `users/{uid}/subscriptions/{subscriptionId}` stores each signed-in browser's Web Push endpoint and encryption keys. Each device has its own subscription.

The Firestore rules scope browser reads and writes to the authenticated UID. The Java Admin SDK used by GitHub Actions will bypass these rules. Store the service account JSON as the `FIREBASE_SERVICE_ACCOUNT_JSON` repository secret and the VAPID private key file's single-line contents as the `VAPID_PRIVATE_KEY` repository secret. `VAPID_PUBLIC_KEY` is already a repository variable for the public site. Never commit any private key.

The scheduled workflow remains an availability-only check until all three notification values are present. Once configured, it reads user settings and subscriptions, records newly available matching slots in a Firestore outbox, sends Web Push notifications, and retries transient delivery failures on later runs. It removes expired subscriptions automatically when a push service responds with HTTP 404 or 410.

To enable the backend, create a Firebase service account JSON key under **Project settings → Service accounts → Generate new private key**. In GitHub, add the complete JSON file contents as the repository secret `FIREBASE_SERVICE_ACCOUNT_JSON`. Add the single-line contents of local `vapid-private.key` as `VAPID_PRIVATE_KEY`. The public `VAPID_PUBLIC_KEY` variable should match the corresponding public key already used by the deployed site. Do not paste either private value into chat or commit it.

## Local preview

Service workers and push require HTTPS or localhost. From the repository root, run a local static server such as:

```sh
python3 -m http.server 8000 --directory site
```

Then open `http://localhost:8000`. The Firebase file must exist before sign-in can work. On iPhone, use the deployed HTTPS site, add it to the Home Screen, open it from the Home Screen, and enable notifications from inside the app.

## Notes

- These rules authorize any Firebase account in the project, but the app has no sign-up flow; only accounts created by the project administrator can sign in.
- Keep the project on Spark. If a Spark quota is exceeded, Firebase can pause that product until its quota resets. Review current limits before launch.
- Browser notification permission is device-specific. Each user should enable notifications separately on each device they want to notify.
